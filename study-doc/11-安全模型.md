# 11 - 安全模型：身份认证与设备确认

> 源码路径：`src/gateway/auth.ts`、`src/infra/device-pairing.ts`、`src/infra/pairing-token.ts`、`src/gateway/server/ws-connection/`、`ui/src/ui/device-identity.ts`、`ui/src/ui/gateway.ts`

---

## 一、Gateway 身份认证概览

所有连接的第一道门，支持五种认证模式（`src/gateway/auth.ts`）：

| 模式 | 方式 | 适合场景 | 安全级别 |
|------|------|---------|---------|
| `token` | Bearer token 比对 | 个人使用、URL 直链 | 中 |
| `password` | 密码比对 | 人工登录 | 中 |
| `tailscale` | Tailscale 网络身份 | 团队内网 | 高 |
| `trusted-proxy` | 反向代理注入 User Header | 企业统一认证 | 高 |
| `none` | 完全放行 | 完全隔离内网 | 无 |

**关键安全设计：**
- 所有 token/password 比对用 `safeEqualSecret()`，常数时间比较，防时序攻击
- 认证失败才计入 Rate Limit，**缺失凭据不扣分**
- HTTP 和 WebSocket Control UI 是两个不同 surface，Tailscale Header 认证只在 `ws-control-ui` surface 开启
- `trusted-proxy` 和 `token` 互斥，同时配置会报错

## 二、设备 ID 是怎么来的

### 服务端（Node.js）

```typescript
// src/infra/device-identity.ts
随机生成 Ed25519 密钥对
  → 公钥原始字节
  → SHA256(公钥字节) → 十六进制字符串 = deviceId
```

存储在 `~/.openclaw/state/identity/device.json`：

```json
{
  "version": 1,
  "deviceId": "a3f8c2...",
  "publicKeyPem": "-----BEGIN PUBLIC KEY-----...",
  "privateKeyPem": "-----BEGIN PRIVATE KEY-----...",
  "createdAtMs": 1234567890
}
```

**启动时自检：** 用私钥对固定字符串 `"openclaw-device-identity-self-check"` 签名再验签，失败则视为损坏，丢弃重新生成。

### 浏览器端（Web）

```typescript
// ui/src/ui/device-identity.ts
// 使用 @noble/ed25519 库
随机生成 Ed25519 私钥（32字节）
  → 推导公钥
  → SHA256(公钥) = deviceId

存入 localStorage["openclaw-device-identity-v1"]：
{
  "version": 1,
  "deviceId": "a3f8c2...",
  "publicKey": "base64url公钥",
  "privateKey": "base64url私钥",
  "createdAtMs": 1234567890
}
```

**关键结论：**

| 情况 | 结果 |
|------|------|
| 正常打开 | 读 localStorage，身份不变 |
| 清空 localStorage | 身份丢失，重新生成，需重新配对 |
| 换浏览器 / 无痕模式 | 新身份 |
| 换电脑 | 新身份 |

**安全边界：** localStorage 同源隔离但未加密，本机有权限的程序能直接读到私钥。这是浏览器的固有限制，比移动端 Keychain / Keystore 弱。

## 三、从输入带 token 的 URL 到连接建立的完整流程

假设 URL：`http://192.168.1.100:18789/?token=abc123`，浏览器是全新的。

### 第一步：浏览器拿到页面

```
GET /?token=abc123 HTTP/1.1
  → 服务器返回 index.html + JS bundle
  → 浏览器执行 main.ts
      → 注册 Service Worker（生产环境）
      → 挂载 <openclaw-app> LitElement 组件
```

### 第二步：JS 藏好 token，清掉 URL

```typescript
// ui/src/ui/app-settings.ts → applySettingsFromUrl()
优先读 #token=（fragment，不发到服务端，不进访问日志）
其次读 ?token=abc123

→ token 写入 localStorage["openclaw-settings"]
→ history.replaceState() 把 token 从地址栏抹掉
```

### 第三步：生成设备身份

localStorage 是空的，现场生成：

```
随机生成 Ed25519 私钥
  → 推导公钥
  → SHA256(公钥) = deviceId = "a3f8c2..."
  → 存入 localStorage["openclaw-device-identity-v1"]
```

### 第四步：建立 WebSocket 连接，发 connect 消息

```
new WebSocket("ws://192.168.1.100:18789")
  → WS open 触发 buildConnectPlan()
```

**buildConnectPlan() 判断：**
- 普通 HTTP + 非 localhost → `crypto.subtle` 不可用 → **跳过设备身份**，只带 token
- HTTPS 或 localhost → 完整走设备身份流程

**connect 消息结构：**

```json
{
  "type": "req",
  "method": "connect",
  "id": "req-001",
  "params": {
    "role": "operator",
    "scopes": ["operator.admin", "operator.read", "operator.write", "operator.approvals", "operator.pairing"],
    "auth": {
      "token": "abc123",
      "deviceToken": "上次颁发的device-token（如果有）"
    },
    "device": {
      "id": "a3f8c2...",
      "publicKey": "base64url公钥",
      "signature": "Ed25519签名",
      "signedAt": 1234567890123,
      "nonce": "服务端下发的随机数"
    },
    "client": {
      "id": "openclaw-control-ui",
      "mode": "webchat",
      "version": "2026.x.x",
      "platform": "web"
    }
  }
}
```

**签名内容（明文拼接，不是加密）：**

```
"v2|{deviceId}|{clientId}|{clientMode}|{role}|{scopes,逗号分隔}|{signedAtMs}|{token}|{nonce}"
```

消息内容本身是明文，签名只是证明"发送者持有对应私钥"，不是加密。

### 第五步：服务端 5 道校验

```
src/gateway/server/ws-connection/message-handler.ts + handshake-auth-helpers.ts

① SHA256(publicKey) == device.id ?          否→关闭
② |now - signedAt| ≤ 2分钟 ?                否→关闭（防重放）
③ nonce == 服务端下发的值 ?                  否→关闭（防重放）
④ Ed25519 验签通过 ?                         否→关闭
   （先尝试 v3 含 platform/deviceFamily，再尝试 v2）
⑤ token "abc123" 与配置匹配 ?               否→关闭
   （safeEqualSecret 常数时间比较）
```

### 第六步：配对 + 颁发 device token

```
设备 a3f8c2... 未见过
  → 本地连接 → 自动静默审批
  → 写入 paired.json：deviceId、公钥、role、approvedScopes
  → ensureDeviceToken()：
      randomBytes(32).toString("base64url") → 43字符随机串
  → 通过 WebSocket 发回 hello-ok
```

### 第七步：浏览器存好 device token

```
localStorage["openclaw.device.auth.v1"] = {
  deviceToken: "zxqwer...",
  role: "operator",
  scopes: [...]
}
```

页面加载完成，UI 可用。

### 之后每次打开浏览器

```
localStorage 里有 device token + 私钥
  → WS connect 消息：带 device token + 签名
  → 服务端验签通过 + device token 匹配
  → 直接放行，不需要 abc123 了
```

> **一句话：** `abc123` 是开门的钥匙，只用一次。进门后服务器发一张门卡（device token），以后刷卡进门。

## 四、公私钥的真实作用

### 本质：证明"我是我"

公私钥不用于加密，只用于**签名/验签**：

| | 加密/解密 | 签名/验签 |
|---|---|---|
| 目的 | 保密 | 证明身份 |
| 私钥做 | 解密 | **签名**（客户端本地做） |
| 公钥做 | 加密 | **验签**（服务端做） |

私钥永远不离开浏览器，只把签名结果发出去。服务端只需公钥即可完成验证。

**Ed25519 数学性质：** 没有私钥算不出对应公钥的合法签名。可以伪造公钥，但伪造不了配套的签名。

### 第一次连接时公私钥没实际意义

第一次连，真正起作用的是共享 token（`abc123`）。

### 之后再连才有实际价值

```
没有共享 token
  → 有 device token + 签名
  → 签名证明"这个 device token 是我的，不是捡来的"
```

### 浏览器端的安全局限

私钥和 device token 都存在 localStorage，没有加密。能读 localStorage 的攻击者两者都能拿到。浏览器端公私钥更多是**架构一致性设计**（与移动端用同一套协议），安全增益有限。移动端私钥存在 Keychain / Keystore，真正拿不走。

## 五、device token 颁发详细过程

### ensureDeviceToken() 逻辑（`src/infra/device-pairing.ts:988`）

不是每次都生成新 token，有复用判断：

```
① 设备在 paired.json 里存在？           否 → 返回 null
② 请求的 role 在审批记录里？             否 → 返回 null
③ 请求的 scopes 在 approved baseline 内？否 → 返回 null

④ 已有 token 且未吊销？
     现有 scopes 覆盖了请求的 scopes？
     issuer.generation 与当前 gateway 一致？
       ✓ 两个都满足 → 直接复用旧 token
       ✗ 任一不满足 → 生成新 token（rotation）

⑤ 全新设备 → 直接生成
```

### token 本身的生成（`src/infra/pairing-token.ts`）

```typescript
randomBytes(32).toString("base64url")
// 256位随机熵，43字符 base64url 字符串
// 不是 JWT，没有签名，就是纯随机数
```

验证时直接字符串比对（`safeEqualSecret()` 常数时间）。

### paired.json 结构

```json
{
  "pairedByDeviceId": {
    "a3f8c2...": {
      "deviceId": "a3f8c2...",
      "publicKey": "base64url公钥",
      "role": "operator",
      "approvedScopes": ["operator.admin", "operator.read", "operator.write"],
      "tokens": {
        "operator": {
          "token": "43字符随机串",
          "role": "operator",
          "scopes": ["operator.admin", "operator.read", "operator.write"],
          "issuer": {
            "kind": "shared-gateway-auth",
            "generation": "abc123"
          },
          "createdAtMs": 1234567890,
          "rotatedAtMs": null,
          "revokedAtMs": null,
          "lastUsedAtMs": 1234567890
        }
      }
    }
  }
}
```

### token rotation 触发条件

| 触发条件 | 原因 |
|---------|------|
| 首次配对 | 没有旧 token |
| gateway 共享 token 轮换 | issuer.generation 对不上 |
| 请求的 scopes 比现有的多 | 现有 token 覆盖不了 |
| 旧 token 已被吊销 | `revokedAtMs` 不为 null |

## 六、密码登录流程

登录页三个输入框：`Gateway URL` / `Token` / `Password`

与 token 方式唯一的区别：

```
token 方式：auth: { token: "abc123" }
密码方式：  auth: { password: "你输的密码" }
```

其他完全相同。服务端用 `safeEqualSecret()` 比对，失败记一次 Rate Limit。

## 七、Tailscale 认证流程

**前提：** 服务器和设备都加入同一 Tailscale 网络，配置 `auth.allowTailscale = true`。

访问 `http://100.x.x.x:18789`，connect 消息里 `auth` 为空。

**服务端校验（`src/gateway/auth.ts → resolveVerifiedTailscaleUser()`）：**

```
① 确认请求来自 Tailscale 本地代理
   → socket.remoteAddress = 127.0.0.1 ✓
   → 有 x-forwarded-for/proto/host 头 ✓

② 读请求头用户身份
   → tailscale-user-login = "you@example.com"

③ 调 Tailscale whois 接口反查
   → GET http://100.100.100.100/localapi/v0/whois?addr=100.x.x.x
   → 拿到真实用户 = "you@example.com"

④ 比对两者是否一致
   → 防止攻击者伪造 tailscale-user-login 请求头
```

验证通过后流程与 token/password 完全一样。

**Tailscale 是什么：** 基于 WireGuard 协议的虚拟局域网工具，把分散在各处的设备连成一个私有网络，Tailscale 服务器只做协调，不看流量内容。

## 八、回放攻击与防护

### 什么是回放攻击

截获合法消息，原封不动再发一遍，不需要知道私钥或密码。

```python
# 攻击者脚本示例
ws.send('{"method":"connect","params":{...截获的内容...}}')
```

### 小龙虾的防护

```
① 时间戳：|now - signedAt| > 2分钟 → 拒绝
   截获的消息 2 分钟后就废

② nonce：服务端下发的一次性随机数，用完失效
   就算 2 分钟内截获，nonce 已用过 → 拒绝
```

### HTTPS 下为什么不能回放

TLS 每次连接都协商新的会话密钥，录下来的密文用旧密钥加密，下次连接服务端用新密钥解不开，直接报错。

**小龙虾仍做消息层防护的原因：**
1. 不是所有人都用 HTTPS，本地 HTTP 部署需要防
2. 纵深防御原则：不能假设下面那层一定安全

## 九、连接建立后的消息安全

连接建立后，后续所有消息都是**明文 JSON**，没有额外签名或加密：

```json
{
  "type": "req",
  "method": "chat.send",
  "params": { "sessionKey": "main", "message": "你好" }
}
```

安全靠传输层（HTTPS/WSS 的 TLS），不靠消息层。连接握手时验过身份，之后在已验证的连接里跑，不需要每条消息再验。

## 十、设备 ID 与数据隔离

设备 ID 目前**只做身份标识，不做数据隔离**。

认证通过后所有设备权限相同，权限粒度是功能级别：

```
operator.admin   → 改配置、管理设备
operator.read    → 读数据
operator.write   → 发消息、操作会话
operator.approvals → 审批 exec 命令
operator.pairing   → 审批设备配对
```

没有"设备 A 只能看会话 1，设备 B 只能看会话 2"的数据级隔离。

## 十一、整体认证架构图

```
连接请求
    │
    ├── HTTP 请求
    │     └── authorizeHttpGatewayConnect()
    │           └── token / password / trusted-proxy / none
    │
    └── WebSocket 请求
          └── WS 升级握手（服务端下发 nonce）
                │
                └── connect 消息
                      │
                      ├─① SHA256(publicKey) == deviceId ?
                      ├─② 时间戳 ≤ 2分钟 ?
                      ├─③ nonce 正确 ?
                      ├─④ Ed25519 验签通过 ?
                      └─⑤ 认证决策（按优先级）
                            ├── bootstrap token（QR 扫码）
                            ├── device token（已配对设备）
                            └── shared secret（token / password / tailscale）
                                    │
                                    ✓ 全部通过
                                    │
                                    ├── requestDevicePairing()
                                    │     └── 本地连接 → 自动静默审批
                                    │
                                    ├── ensureDeviceToken()
                                    │     └── randomBytes(32).toString("base64url")
                                    │
                                    └── hello-ok（带 device token）
                                          └── 浏览器写入 localStorage
```
